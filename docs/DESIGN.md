# Re:Start Quest MVP 설계

상태: TASK-001 생성·저장과 TASK-004 기록·재설계 통합본, TASK-005 대시보드 구현 전 계약의 정본. 근거: [제품 브리프](PROJECT_BRIEF.md). 이 문서는 구현된 동작과 후속 대시보드 계약을 구분하며, 실행·검증 결과는 각 구현과 QA 산출물에서 확인한다.

## 제품 방향과 범위

사용자는 지금 쓸 수 있는 시간과 현재 상태만 입력해 오늘 바로 시작할 작은 구직 행동 하나를 받는다. 완료나 실패는 사람의 능력 평가가 아니라 다음 행동을 정하기 위한 기록이다. 첫 진입 화면의 주 행동은 `오늘의 퀘스트 만들기`이며, 저장된 퀘스트가 있다면 같은 화면에서 다시 찾을 수 있어야 한다.

| 단계 | 사용자 흐름과 이번 단계의 결과 | 뒤로 미루는 것 |
| --- | --- | --- |
| 1. 생성·저장 (기존 구현) | 시간·상태 입력 → 규칙 기반 퀘스트 생성 → 저장 목록 확인 → 새로고침·서버 재시작 후 같은 ID 확인 | 완료·실패 기록, 재설계, 집계 대시보드 |
| 2. 기록·재설계 (현재 통합 slice) | 완료 또는 실패 이유 기록 → 실패 이유에 맞춘 더 작은 대안 생성 → 부모·자식 이력 확인 | 전체 집계 대시보드 |
| 3. 대시보드·통합 | 실제 저장 기록의 상태·이력·다음 행동 표시 → 전체 흐름을 데스크톱·모바일에서 검증 | 브리프의 제외 범위 |

첫 단계의 저장 목록은 대시보드의 집계나 더미 이력으로 표현하지 않는다. 이력서 첨삭, 채용 공고 수집, 로그인, 외부 AI, 배포는 브리프의 제외 범위를 따른다.

## 기술·실행 구조

- Node.js 22 이상, ECMAScript 모듈의 단일 HTTP 서버와 브라우저 기본 HTML·CSS·JavaScript를 사용한다. 첫 slice에 유료 API, 데이터베이스 서버, 번들러, 계정이 필요하지 않다. 단일 서버가 정적 화면과 `/api/*`를 같은 origin에서 제공한다. 화면은 실제 API 응답을 렌더링한다.
- 정적 화면은 `client`에서 `npm run build`를 실행해 `client/dist`에 만든다. 저장소 루트에서 `npm start`를 실행하기 전에 빌드한다.
- 서버 진입점과 `createQuestServer`의 기본 정적 경로는 실행 디렉터리 기준 `client/dist`다. 서버는 `/`, `/app.js`, `/quest-app.js`, `/styles.css`를 API와 같은 origin에서 제공한다. `QUEST_PUBLIC_DIR`를 설정하면 서버 진입점의 경로를, `createQuestServer`를 직접 호출할 때는 `publicDir` 옵션으로 경로를 재정의한다.
- 서버가 입력 검증, 퀘스트 선택, ID 생성, 저장을 소유한다. 화면은 서버가 반환한 퀘스트를 임의로 다시 계산하거나 성공 상태를 먼저 표시하지 않는다.
- 저장소는 단일 프로세스의 로컬 JSON 스냅샷이다. `QUEST_DATA_FILE`이 설정되면 그 경로, 아니면 저장소 실행 디렉터리의 `data/quests.json`을 쓴다. 설치·실행·테스트 명령과 비밀값 없는 설정 예제는 [README](../README.md)에 기록한다. 사용자의 실제 기록 파일은 Git에 포함하지 않도록 로컬 데이터 경로를 무시한다.
- 첫 slice에는 두 개 이상의 서버 프로세스가 같은 파일에 쓰는 배포를 지원하지 않는다. 다중 인스턴스가 필요해지면 파일 잠금 또는 트랜잭션 DB로 저장 계약을 교체해야 한다.

## 입력과 규칙 기반 생성

`availableMinutes`는 정수 5~120, `energy`는 소문자 문자열 `low`·`medium`·`high` 중 하나다. 시간은 오늘 이 행동에 쓸 수 있는 분량이며 상태는 의욕이나 능력 점수가 아니라 사용자가 선택한 현재 에너지다. 문자열 숫자, 소수, `null`, 누락, 범위 밖 값, 정의되지 않은 상태와 알 수 없는 요청 필드는 거절한다. 화면에는 숫자 입력의 최솟값·최댓값과 상태의 쉬운 설명을 보여 주되 서버가 같은 규칙을 다시 검사한다.

서버는 아래 표에서 **선택한 상태의 행 중 `estimatedMinutes <= availableMinutes`인 가장 긴 행**을 고른다. 동률은 표의 순서로 고정한다. 이 규칙은 모든 유효 입력에 최소 5분 퀘스트를 제공하고, 제안 시간은 항상 입력 시간을 넘지 않는다. 매 요청은 새 퀘스트 한 개를 저장한다. `description`에는 행동의 끝이 보이는 한 문장만 넣고 결과물의 품질이나 취업 성공을 약속하지 않는다.

| energy | estimatedMinutes | title | description |
| --- | ---: | --- | --- |
| low | 5 | 관심 직무 한 개 적기 | 떠오르는 직무 이름 한 개를 메모한다. |
| low | 10 | 관심 회사 한 곳 찾아보기 | 관심 회사 한 곳의 이름과 이유 한 줄을 적는다. |
| low | 15 | 공고 한 개 읽기 | 공고 한 개를 읽고 눈에 띈 요구사항 한 줄을 적는다. |
| medium | 5 | 지원 후보 한 곳 저장하기 | 나중에 볼 회사나 공고 한 곳을 저장한다. |
| medium | 10 | 공고의 핵심 요건 표시하기 | 공고 한 개에서 핵심 요건 한 가지를 적는다. |
| medium | 20 | 경험 한 항목 초안 쓰기 | 지원에 쓸 경험 한 항목을 두세 문장으로 적는다. |
| high | 5 | 지원 후보 한 곳 저장하기 | 나중에 볼 회사나 공고 한 곳을 저장한다. |
| high | 15 | 경험 사례 하나 고르기 | 지원 직무와 닿는 경험 사례 하나를 골라 제목을 적는다. |
| high | 25 | 경험 사례 한 항목 작성하기 | 사례 하나의 상황·행동·결과를 짧게 적는다. |

제목과 설명은 서버의 규칙 결과다. 행동에 실제 채용 공고 데이터 연결이 필요하지 않으며, 사용자가 자신의 자료로 실행할 수 있다. 같은 입력이라도 POST마다 새 ID와 시각을 갖는다.

## 데이터 모델과 영속 저장

저장 파일의 최상위 형식은 `{ "schemaVersion": 1, "quests": [...] }`다. 서버는 각 퀘스트에 다음 필드를 저장하고 API로 동일한 필드를 반환한다. ID는 서버가 만든 UUID 문자열, 시각은 UTC ISO 8601 문자열이다.

| 필드 | 타입과 첫 단계 값 | 2단계까지의 의미 |
| --- | --- | --- |
| `id` | string, UUID | 생성부터 재조회까지 불변인 식별자 |
| `createdAt` | string, UTC ISO 8601 | 생성 시각; 목록은 내림차순, 동시각이면 `id` 오름차순 |
| `availableMinutes` | integer 5~120 | 원본 생성 당시 사용자 입력; 자식은 부모 값을 상속 |
| `energy` | `low`·`medium`·`high` | 원본 생성 당시 사용자 입력; 자식은 부모 값을 상속 |
| `title`, `description` | 비어 있지 않은 string | 생성 당시 확정한 행동 문구; 재조회 시 다시 생성하지 않음 |
| `estimatedMinutes` | positive integer, `<= availableMinutes` | 이번 단계는 표의 5~25분, 재설계 단계는 5분 미만도 허용 |
| `status` | `pending` | `pending`에서 `completed` 또는 `failed`로 한 번만 전이 |
| `failureReason` | `null` | 실패할 때만 아래 지원 코드 중 하나로 변경 |
| `completedAt`, `failedAt` | `null` | 상태 전이 시 해당 시각만 설정 |
| `parentQuestId` | `null` | 재설계 대안의 직전 원본 ID; 원본은 null |
| `rootQuestId` | 자기 `id` | 재설계 체인 첫 퀘스트 ID, 자식은 부모의 값을 상속 |

첫 단계의 불변조건은 `status=pending`, 완료·실패 시각과 실패 이유는 null, `parentQuestId=null`, `rootQuestId=id`다. 2단계의 상태 전이, 이유 분류, 자식 생성과 조회는 아래 **기록·재설계 계약**을 따른다. 원본이 5분이라도 더 짧은 대안을 허용하므로 5분 입력 하한을 대안의 예상 시간 하한으로 사용하지 않는다.

쓰기 요청은 서버 프로세스 안에서 직렬화한다. 기존 메모리 스냅샷을 복사해 변경·검증한 다음, 같은 디렉터리의 고유 임시 파일에 전체 JSON을 쓰고 파일을 동기화한 뒤 기존 파일로 원자적 이름 변경한다. 이름 변경이 성공한 뒤에만 메모리 스냅샷을 교체하고 해당 endpoint의 성공 응답을 보낸다. 실패하면 메모리와 기존 확정 파일을 유지하고 오류를 응답한다. 임시 파일만 남은 경우 재시작 시 정본으로 사용하지 않는다. 시작할 때 파일이 없으면 빈 목록으로 시작하고, 파일이 손상되거나 지원하지 않는 `schemaVersion`이면 덮어쓰지 않고 서버 시작을 실패시킨다. 저장 경로는 테스트마다 격리한다.

## HTTP 계약 v1

API 응답과 POST 본문은 JSON이다. 정상 응답과 오류 응답 모두 `Content-Type: application/json; charset=utf-8`을 쓴다. 시간과 ID는 서버 값이 정본이다. 알 수 없는 필드는 서버가 거절한다. POST는 `Content-Type: application/json`과 UTF-8 JSON 객체만 받는다.

### `POST /api/quests`

요청: `{ "availableMinutes": 20, "energy": "medium" }`

성공: `201 Created`. 본문은 아래 형태이며, 예시의 ID·시각은 실행할 때 달라진다.

```json
{
  "quest": {
    "id": "6d4e86be-c832-4a80-8853-1b0d7a11a723",
    "createdAt": "2026-10-09T00:00:00.000Z",
    "availableMinutes": 20,
    "energy": "medium",
    "title": "경험 한 항목 초안 쓰기",
    "description": "지원에 쓸 경험 한 항목을 두세 문장으로 적는다.",
    "estimatedMinutes": 20,
    "status": "pending",
    "failureReason": null,
    "completedAt": null,
    "failedAt": null,
    "parentQuestId": null,
    "rootQuestId": "6d4e86be-c832-4a80-8853-1b0d7a11a723"
  }
}
```

### `GET /api/quests`

성공: `200 OK`, `{ "quests": [<quest>, ...] }`. `<quest>`는 POST의 `quest`와 같은 스키마다. 빈 저장소는 `{ "quests": [] }`다. 정렬은 `createdAt` 내림차순, 같으면 `id` 오름차순이다. 브라우저는 이 응답을 저장 목록의 유일한 출처로 사용한다. 첫 slice의 조회 endpoint는 목록뿐이다.

### 오류

모든 오류의 본문은 `{ "error": { "code": "...", "message": "사용자가 이해할 수 있는 문장", "fields": {} } }`다. `fields`는 필드별 오류가 없을 때에도 빈 객체다. 내부 파일 경로나 원문 예외는 포함하지 않는다. 서버는 오류 발생 시 성공 응답이나 저장 완료 표시를 내지 않는다.

| HTTP | `code` | 조건 | 저장 영향 |
| ---: | --- | --- | --- |
| 400 | `INVALID_INPUT` | 입력 누락·형식·범위·상태·알 수 없는 필드 | 없음; `fields.availableMinutes` 또는 `fields.energy` 등으로 표시 |
| 400 | `INVALID_JSON` | 파싱할 수 없는 JSON 또는 객체가 아닌 본문 | 없음 |
| 415 | `UNSUPPORTED_MEDIA_TYPE` | JSON이 아닌 POST 본문 | 없음 |
| 413 | `PAYLOAD_TOO_LARGE` | POST 본문 16 KiB 초과 | 없음 |
| 404 | `NOT_FOUND` | 정의되지 않은 `/api/*` 경로 | 없음 |
| 405 | `METHOD_NOT_ALLOWED` | 정의된 API 경로의 지원하지 않는 메서드 | 없음 |
| 503 | `PERSISTENCE_ERROR` | 확정 저장을 완료하지 못함 또는 저장 읽기 불가 | 새 퀘스트 성공으로 표시하지 않음 |
| 500 | `INTERNAL_ERROR` | 그 밖의 예상하지 못한 서버 오류 | 새 퀘스트 성공으로 표시하지 않음 |

화면 계약 fixture의 대표 오류 응답은 다음과 같다. 503 fixture에서는 `code`를 `PERSISTENCE_ERROR`, `message`를 `저장에 실패했습니다. 잠시 후 다시 확인해 주세요.`, `fields`를 빈 객체로 둔다.

```json
{
  "error": {
    "code": "INVALID_INPUT",
    "message": "시간은 5분에서 120분 사이의 정수로 입력해 주세요.",
    "fields": { "availableMinutes": "5~120 사이의 정수가 필요합니다." }
  }
}
```

저장 중 통신이 끊긴 경우 화면은 성공을 추측하지 않고 GET으로 목록을 다시 읽어 상태를 확인한다. POST 재시도는 새 퀘스트를 만들 수 있으므로 자동 재시도를 하지 않는다.

## 기록·재설계 계약 (TASK-004, 현재 통합본)

이 절은 기존 `POST /api/quests`와 `GET /api/quests`를 유지하면서 통합된 2단계 계약이다. 아래 JSON과 ID는 계약 예시이며 실제 실행 결과는 아니다. 각 쓰기 성공 응답의 `quest`는 위 데이터 모델의 **전체 13개 필드**를 담고, `GET /api/quests`는 자식까지 같은 평면 목록에 포함한다. `id`는 서버가 생성한 UUID이며 경로의 `{id}`는 저장된 퀘스트 ID다.

### 상태와 실패 이유

| 현재 상태 | 허용 요청 | 확정 후 필드 | 그 밖의 전이 |
| --- | --- | --- | --- |
| `pending` | `complete` 또는 `fail` 중 먼저 확정된 한 번 | 완료: `status=completed`, `completedAt`만 UTC 시각, `failureReason=failedAt=null`. 실패: `status=failed`, `failureReason`은 아래 코드, `failedAt`만 UTC 시각, `completedAt=null` | 두 요청이 동시에 들어와도 하나만 성공 |
| `completed` | 상태 전이 없음 | 모든 상태·시각·이유 불변 | 완료 재요청과 실패 요청 모두 `409 QUEST_ALREADY_RESOLVED` |
| `failed` | 해당 퀘스트에 자식이 없고 축소 가능할 때 `redesign` 한 번 | 실패 이유와 시각은 원본에 유지하고 별도 `pending` 자식 한 개 추가 | 완료·실패 재요청은 `409 QUEST_ALREADY_RESOLVED` |

`failureReason`은 실패 시 필수인 **코드 한 개**다. 화면에서는 다음 한국어 레이블을 선택지로 보여 주고 API에는 코드만 전송한다. 누락, `null`, 빈 문자열, 지원하지 않는 문자열, 다른 타입, 추가 필드는 `400 INVALID_INPUT`으로 거절한다. 자유 입력 문장을 파일에 추가하지 않는다.

| 코드 | 화면 레이블 | 자식의 예상 시간 `m` (`p`=실패한 부모의 `estimatedMinutes`) | 자식 제목 | 자식 설명 템플릿 |
| --- | --- | ---: | --- | --- |
| `time_shortage` | 시간이 부족했어요 | `max(1, floor(p / 2))` | 짧게 시작하기 | `{루트 제목}를 {m}분 동안만 시작하고 멈춘다.` |
| `low_energy` | 지금은 에너지가 부족했어요 | `max(1, floor(2p / 3))` | 자료 한 가지 준비하기 | `{루트 제목}를 시작할 자료나 메모 한 가지를 준비한다.` |
| `unclear_start` | 어디서 시작할지 막막했어요 | `max(1, floor(p / 3))` | 첫 단서 한 줄 적기 | `{루트 제목}의 첫 단서를 한 줄로 적는다.` |

서버는 표의 고정 제목·설명 템플릿과 루트 퀘스트의 제목으로 자식 문구를 만든다. 이를 통해 같은 부모·이유에서 같은 행동 문구와 시간 규칙이 나온다. 새 `id`와 `createdAt`만 생성 시 달라진다. 세 규칙 모두 `p >= 2`에서 정수 `1 <= m < p`를 보장하며, 이유에 맞는 **예상 시간 축소**를 기계적으로 확인할 수 있다. 자식의 `availableMinutes`와 `energy`는 원래 사용자 입력 맥락을 보존하도록 부모에게서 상속하고, `estimatedMinutes`만 새 제안 시간으로 저장한다. 자식은 새 `id`, `createdAt`, `status=pending`, 세 상태 부속 필드 `null`, `parentQuestId=부모.id`, `rootQuestId=부모.rootQuestId`를 가진다. 자식도 실패하면 같은 규칙으로 한 단계 더 재설계할 수 있다. `p=1`에서는 어떤 이유에도 더 작은 양의 정수 시간을 만들 수 없으므로 자식을 만들지 않고 `409 REDESIGN_LIMIT_REACHED`를 반환한다. 5분은 **새 퀘스트 생성 입력**의 하한일 뿐 자식의 시간 하한이 아니다.

한 부모에게 자식은 최대 한 개다. 이미 자식이 있다면 이유나 요청 시점과 관계없이 `409 QUEST_ALREADY_REDESIGNED`를 반환하고 같은 자식을 다시 만들지 않는다. `pending` 또는 `completed`의 재설계는 `409 QUEST_NOT_FAILED`다. 자식이 있는 부모의 실패 이유를 바꾸는 API는 없다. 완료된 퀘스트도 재설계할 수 없다. 서버는 부모 상태·자식 존재·1분 경계를 **직렬화된 쓰기 작업 안에서 다시 검사**해 동시 요청이 둘 다 성공하지 못하게 한다.

### HTTP 요청·응답

모든 쓰기 endpoint는 `Content-Type: application/json`의 UTF-8 JSON 객체를 받는다. `complete`와 `redesign`은 빈 객체 `{}`가 유일한 유효 본문이며, `fail`은 `failureReason`만 받는다. 16 KiB 제한, `INVALID_JSON`(400), `UNSUPPORTED_MEDIA_TYPE`(415), `PAYLOAD_TOO_LARGE`(413), 알 수 없는 필드의 `INVALID_INPUT`(400)은 기존 생성 API와 같다. 성공과 오류 모두 `application/json; charset=utf-8`이다. 예시 UUID와 시각은 설명용이다.

`POST /api/quests/11111111-1111-4111-8111-111111111111/complete` 요청 본문 `{}` → `200 OK`:

```json
{
  "quest": {
    "id": "11111111-1111-4111-8111-111111111111",
    "createdAt": "2026-10-09T00:00:00.000Z",
    "availableMinutes": 20,
    "energy": "medium",
    "title": "경험 한 항목 초안 쓰기",
    "description": "지원에 쓸 경험 한 항목을 두세 문장으로 적는다.",
    "estimatedMinutes": 20,
    "status": "completed",
    "failureReason": null,
    "completedAt": "2026-10-09T00:05:00.000Z",
    "failedAt": null,
    "parentQuestId": null,
    "rootQuestId": "11111111-1111-4111-8111-111111111111"
  }
}
```

별도로 생성한 퀘스트에 `POST /api/quests/22222222-2222-4222-8222-222222222222/fail` 요청 본문 `{ "failureReason": "time_shortage" }` → `200 OK`:

```json
{
  "quest": {
    "id": "22222222-2222-4222-8222-222222222222",
    "createdAt": "2026-10-09T00:00:00.000Z",
    "availableMinutes": 20,
    "energy": "medium",
    "title": "경험 한 항목 초안 쓰기",
    "description": "지원에 쓸 경험 한 항목을 두세 문장으로 적는다.",
    "estimatedMinutes": 20,
    "status": "failed",
    "failureReason": "time_shortage",
    "completedAt": null,
    "failedAt": "2026-10-09T00:05:00.000Z",
    "parentQuestId": null,
    "rootQuestId": "22222222-2222-4222-8222-222222222222"
  }
}
```

이 실패 퀘스트에 `POST /api/quests/22222222-2222-4222-8222-222222222222/redesign` 요청 본문 `{}` → `201 Created`. 부모의 실패 기록은 그대로 두고 아래 자식을 같은 스냅샷에 추가한다:

```json
{
  "quest": {
    "id": "33333333-3333-4333-8333-333333333333",
    "createdAt": "2026-10-09T00:06:00.000Z",
    "availableMinutes": 20,
    "energy": "medium",
    "title": "짧게 시작하기",
    "description": "경험 한 항목 초안 쓰기를 10분 동안만 시작하고 멈춘다.",
    "estimatedMinutes": 10,
    "status": "pending",
    "failureReason": null,
    "completedAt": null,
    "failedAt": null,
    "parentQuestId": "22222222-2222-4222-8222-222222222222",
    "rootQuestId": "22222222-2222-4222-8222-222222222222"
  }
}
```

`GET /api/quests/{id}/history`는 루트 또는 자식 ID 모두 받는다. `200 OK` 응답은 `{ "rootQuestId": "<루트 ID>", "quests": [<루트 quest>, <첫 자식 quest>, ...] }` 형태이며, 각 항목은 위의 **전체 quest 객체**다. 예시 자식 ID `33333333-3333-4333-8333-333333333333`으로 조회하면 `rootQuestId`는 `22222222-2222-4222-8222-222222222222`, 배열은 바로 위 실패 원본과 자식의 두 객체 순서다. 응답은 요청한 노드까지만 자르지 않고 같은 루트의 최신 자손까지 포함한다. 한 부모에 자식이 하나뿐이므로 순서는 루트 → 자식 → 후손으로 유일하다. 해당 ID가 없으면 `404 NOT_FOUND`다. 화면은 이 응답과 기존 GET 목록을 재조회해 상태·관계를 표시하며, ID나 시간만으로 관계를 추측하지 않는다.

위 완료 예시 ID에 `POST /api/quests/11111111-1111-4111-8111-111111111111/complete` 본문 `{}`를 다시 보내거나 같은 ID의 `/fail`에 `{ "failureReason": "time_shortage" }`를 보내면 둘 다 `409 Conflict`이고 다음 본문을 받는다. 확정된 완료 기록은 바뀌지 않는다.

오류 본문은 기존 `{ "error": { "code": "...", "message": "...", "fields": {} } }` 형식을 유지한다. 경로 ID의 형식이 잘못됐거나 실패 이유가 유효하지 않으면 `400 INVALID_INPUT`과 각각 `fields.id` 또는 `fields.failureReason`을 반환한다. 형식은 맞지만 저장되지 않은 ID는 `404 NOT_FOUND`다. 쓰기 요청은 본문 검증, ID 형식, ID 존재, 상태·자식 충돌 순서로 판정하며 확정 전 실패한 요청은 메모리와 저장 파일을 바꾸지 않는다. 대표 충돌·입력 응답:

```json
{ "error": { "code": "QUEST_ALREADY_RESOLVED", "message": "이미 기록된 퀘스트입니다. 저장된 상태를 확인해 주세요.", "fields": {} } }
```

위 실패 예시 ID에 `POST /api/quests/22222222-2222-4222-8222-222222222222/redesign` 본문 `{}`를 다시 보내면 `409 Conflict`와 `{ "error": { "code": "QUEST_ALREADY_REDESIGNED", "message": "이미 더 작은 행동이 있습니다. 이력을 확인해 주세요.", "fields": {} } }`를 받고 기존 자식 ID는 유지된다. `estimatedMinutes=1`인 실패 퀘스트에 같은 요청을 보내면 `409 Conflict`와 `{ "error": { "code": "REDESIGN_LIMIT_REACHED", "message": "더 줄일 수 없는 1분 행동입니다. 잠시 쉬거나 새 퀘스트를 만들어 보세요.", "fields": {} } }`를 받는다.

```json
{ "error": { "code": "INVALID_INPUT", "message": "실패 이유를 선택해 주세요.", "fields": { "failureReason": "지원하는 실패 이유를 선택해 주세요." } } }
```

| HTTP | `code` | 조건과 화면 처리 |
| ---: | --- | --- |
| 409 | `QUEST_ALREADY_RESOLVED` | 완료·실패의 중복 또는 역방향 요청; GET으로 확정 상태 확인 |
| 409 | `QUEST_NOT_FAILED` | 실패로 확정하지 않은 부모의 재설계 |
| 409 | `QUEST_ALREADY_REDESIGNED` | 같은 부모의 재설계 중복; history GET으로 기존 자식 확인 |
| 409 | `REDESIGN_LIMIT_REACHED` | 실패한 부모가 이미 1분; 새 퀘스트 시작 또는 잠시 쉬기 안내 |
| 503 | `PERSISTENCE_ERROR` | 상태·자식 스냅샷 확정 실패; 성공으로 표시하지 않음 |
| 500 | `INTERNAL_ERROR` | 예상하지 못한 처리 오류; 성공으로 표시하지 않음 |

완료·실패·자식 추가는 모두 `schemaVersion: 1`의 **전체 스냅샷을 한 번 교체**하는 쓰기다. 기존 생성 API가 저장한 v1 `pending` 원본은 필드를 보충하거나 새 버전으로 변환하지 않고 그대로 읽는다. 첫 기록 전에는 디스크 내용도 바꾸지 않는다. 로드 시에는 각 상태의 이유·시각 조합, 부모 참조 존재와 `failed` 상태, 부모당 자식 한 개, 루트 ID 일치와 순환 부재를 확인한다. 기존 정상 v1 생성 기록은 이 검사에 그대로 적합하다. 어긋난 파일은 자동 보정하거나 덮어쓰지 않고 시작을 실패시킨다. 상태 전이에서는 같은 ID 객체의 `status`와 해당 이유·시각만 바꾸며 생성 정보와 관계 ID를 보존한다. 재설계에서는 원본을 수정하지 않고 자식만 추가한다. 각 요청의 충돌 검사는 직렬화 작업 안에서 현재 스냅샷을 기준으로 다시 수행한다. 임시 파일 쓰기·동기화·원자적 이름 변경이 성공한 뒤에만 메모리 교체와 `200`/`201`을 반환한다. 저장에 실패하면 `503`과 함께 이전 메모리·정본 파일을 유지한다. 이미 지원하지 않는 버전이나 손상된 파일은 시작 시 덮어쓰지 않고 실패시킨다. 성공 응답을 받기 전 연결이 끊기면 화면은 자동 POST 재전송 없이 GET 목록·history로 실제 확정 상태를 확인한다.

### 화면과 검증 경계

기존 목록의 `pending` 항목에 `완료 기록`과 `실패 이유 선택` 행동을 둔다. 실패 선택지는 위의 세 레이블이며 선택 전에는 저장 버튼을 활성화하지 않는다. `failed` 항목은 이유를 비난 없이 보여 주고, 자식이 없을 때 `더 작은 행동 제안`을 제공한다. 대안은 예상 시간과 축소된 행동, 부모·루트 관계를 한 흐름에서 읽을 수 있게 보여 준다. 완료된 항목은 확정 시각을 보여 주되 다시 완료·실패 버튼을 내지 않는다. 1분 한계와 409 응답은 다음 선택을 돕는 안내로 표현한다. 예: `이번에는 시간이 부족했군요. 10분만 시작해 볼까요?`, `지금은 1분짜리 행동입니다. 잠시 쉬거나 새 퀘스트를 만들어 보세요.`. 사람의 의지나 능력을 평가하는 문구는 쓰지 않는다.

화면은 새 조작의 진행 중 중복 클릭을 막고, 서버 성공 응답 또는 재조회로 확인한 결과만 확정 상태로 표시한다. 400의 `fields.failureReason`은 이유 선택 근처에, 409는 해당 퀘스트 근처에, 503과 통신 오류는 목록·이력의 재조회 동작과 함께 표시한다. 읽기 실패 시 이전 데이터를 새 성공처럼 강조하지 않는다. `GET /api/quests/{id}/history`로 루트·자식 관계를 읽고, 새로고침 뒤에도 같은 ID·상태·이유·관계를 다시 표시한다. 데스크톱 1280px와 모바일 390px에서 이유 선택, 완료·실패·재설계 버튼, 상태·오류·이력이 겹치거나 가려지지 않아야 한다. 상태·오류는 색만으로 구분하지 않고 키보드로 조작할 수 있어야 한다.

서버의 독립 fixture는 세 이유 각각의 축소 계산, 2분→1분과 1분 한계, 완료·실패 동시 요청, 중복·역방향 전이와 부모당 중복 자식, 유효하지 않은 본문·ID·이유, 503에서 메모리·파일 불변, 기존 v1 파일 로드와 재시작 후 동일 ID·관계를 검증한다. 화면 fixture는 각 응답의 문구·버튼 상태·관계 표시와 400·409·503·연결 단절을 검증하며 실제 저장 성공을 주장하지 않는다. **두 구현이 합쳐진 동일 head**의 QA는 실제 HTTP와 브라우저에서 생성→완료, 별도 생성→실패→이유별 재설계→history, 중복 요청과 오류, 새로고침·서버 재시작, 1280px·390px 조작을 확인한다. 대시보드 집계와 전체 MVP 완료는 후속 slice와 최종 통합 gate에서 판정한다.

현재 서버 테스트는 실제 HTTP·파일 저장·재시작을, 화면 단위 테스트와 `smoke`는 fixture 기반 표시·조작을 각각 검사한다. `client/test/e2e.js`는 빌드한 화면과 실제 저장 서버를 함께 실행해 생성·완료, 세 실패 이유별 기록·재설계·history, 중복·역방향 요청과 저장 불변, 400·409·실제 저장 실패 503·통신 단절, 새로고침·서버 재시작, 데스크톱 1280px·모바일 390px을 검증한다. 브라우저 검증의 실제 실행 결과는 통합 head의 QA 근거로 남기며, fixture 결과를 실제 저장 연결의 증거로 사용하지 않는다. 저장 이력 기반 대시보드와 전체 MVP 흐름은 후속 slice의 검증 대상이다.

## 대시보드 계약 (TASK-005, 구현 전)

### `GET /api/dashboard`: 확정 스냅샷의 읽기 전용 투영

요청 본문과 필수 query parameter가 없는 `GET`이다. 성공은 `200 OK`, `Content-Type: application/json; charset=utf-8`, `Cache-Control: no-store`로 응답한다. 다른 메서드는 기존 API와 같은 구조의 `405 METHOD_NOT_ALLOWED` 및 `Allow: GET`을 반환한다. 한 요청의 `counts`, `histories`, `nextAction`은 **동일한 확정 `schemaVersion: 1` 메모리 스냅샷**에서 계산한다. 아직 확정되지 않은 쓰기나 실패한 쓰기의 후보 스냅샷은 포함하지 않는다. 이 GET은 저장 파일·메모리 스냅샷·퀘스트 시각을 수정하거나 복구하지 않는다. 별도 집계 파일과 새 저장 필드는 만들지 않는다. 기존 `GET /api/quests`, `GET /api/quests/{id}/history`, 모든 POST의 응답·상태 코드와 v1 파일 형식은 그대로 유지한다.

응답 형태는 `{ "counts": { "pending": 0, "completed": 0, "failed": 0, "redesigned": 0 }, "histories": [], "nextAction": { "kind": "create", "questId": null, "rootQuestId": null } }`이다. 필드 정의는 다음과 같다.

| 필드 | 의미 |
| --- | --- |
| `counts.pending`, `completed`, `failed` | 전체 `quests` 배열의 **각 퀘스트 객체 한 건**을 현재 `status`에 정확히 한 번 집계한 0 이상의 정수. 세 값의 합은 전체 객체 수다. 루트 수나 완료·실패 이벤트 수가 아니다. |
| `counts.redesigned` | `parentQuestId !== null`인 자식 객체의 총수. 상태와 무관하며 `pending`·`completed`·`failed` 중 하나에도 동시에 포함된다. 실패한 부모 수와 혼동하지 않는다. |
| `histories` | 루트(`parentQuestId === null`)마다 한 항목. 루트의 `createdAt` 내림차순, 같으면 루트 `id` 오름차순으로 정렬한다. |
| `histories[].rootQuestId` | 루트의 `id`. 각 항목의 `quests`는 기존 history API와 같은 **전체 13개 필드의 quest 객체** 배열이다. |
| `histories[].quests` | `rootQuestId`부터 `parentQuestId`를 따라 첫 자식·후손까지 잇는 순서. 생성 시각이나 파일 배열 순서로 체인을 추측하지 않는다. 모든 저장 객체는 정확히 한 이력에 포함된다. 순환·누락·중복 연결로 이를 만족하지 못하면 부분 결과 대신 아래의 `500` 오류를 반환한다. |
| `nextAction` | `{ "kind": ..., "questId": string|null, "rootQuestId": string|null }`. `kind`는 `resume`(진행 가능한 퀘스트 실행), `redesign`(실패 이유를 기록한 퀘스트 축소), `rest_or_create`(1분 한계에서 쉬거나 새 퀘스트), `create`(새 퀘스트 만들기) 중 하나다. 두 ID는 선택된 퀘스트와 루트를 가리키며 `create`에서만 모두 `null`이다. 제목·시간·이유는 해당 이력의 저장 객체에서 읽는다. |

다음 행동은 각 이력의 **맨 끝 자손 한 개**만 후보로 삼아 아래 순서로 고른다. 이전에 실패한 조상을 다시 실행하거나 이미 자식이 있는 부모를 다시 재설계하지 않는다.

1. 끝 자손이 `pending`인 이력이 하나라도 있으면 `resume`을 고른다. 여러 개면 끝 자손 `createdAt` 내림차순, 동시각이면 끝 자손 `id` 오름차순이다.
2. 그런 이력이 없고 끝 자손이 `failed`이며 `estimatedMinutes > 1`인 이력이 있으면 같은 정렬 규칙으로 `redesign`을 고른다. 실패 이유는 이미 저장된 값이어야 한다.
3. 앞의 후보가 없고 끝 자손이 `failed`이며 `estimatedMinutes === 1`인 이력이 있으면 같은 정렬 규칙으로 `rest_or_create`를 고른다. 이 경우 재설계 POST를 권하지 않는다.
4. 빈 저장소이거나 모든 끝 자손이 `completed`이면 `create`를 고른다. 우선순위는 퀘스트의 시각이 더 최신인지보다 앞서며, `completedAt`·`failedAt`은 후보 정렬에 사용하지 않는다. 유효한 v1 스냅샷에서 각 루트는 단일 체인이므로 끝 자손도 하나다.

빈 입력 `{ "schemaVersion": 1, "quests": [] }`의 기대 응답은 위 응답 형태 그대로다. 화면은 네 수치를 모두 `0`으로 표시하고 `아직 기록이 없어요. 오늘의 첫 퀘스트를 만들어 보세요.`와 생성 폼으로 가는 행동을 제공한다. 이를 통신 오류의 0건 대체 표시로 사용하지 않는다.

복합 이력의 검증 fixture는 다음과 같다. 표의 각 행은 위 **데이터 모델과 영속 저장**의 전체 quest 객체를 뜻한다. 모든 행의 `energy`는 `medium`, A·B의 `availableMinutes`는 10, C·D·E·F는 5다. `title`·`description`은 앞의 생성·재설계 규칙에 따른 비어 있지 않은 문장이다. 표에서 지정하지 않은 `completedAt`·`failedAt`은 null이다. C의 `completedAt`은 `2026-10-09T10:00:30.000Z`, A·D·F의 `failedAt`은 각각 `2026-10-09T09:05:00.000Z`·`2026-10-09T10:01:10.000Z`·`2026-10-09T10:01:40.000Z`다. `id`의 앞자리로 표시한 A~F는 아래 UUID에 대응한다. B는 A의 자식이고 F는 D의 자식이다. B와 E의 생성 시각을 같게 하여 동률 규칙도 검증한다.

입력 스냅샷은 `{ "schemaVersion": 1, "quests": [A, B, C, D, E, F] }`이며 A~F에는 표와 데이터 모델의 전체 필드가 들어간다.

| 약칭·`id` | `createdAt` (UTC) | `parentQuestId` / `rootQuestId` | `status` / `failureReason` | `estimatedMinutes` |
| --- | --- | --- | --- | ---: |
| A `11111111-1111-4111-8111-111111111111` | `2026-10-09T09:00:00.000Z` | null / A | `failed` / `time_shortage` | 10 |
| B `22222222-2222-4222-8222-222222222222` | `2026-10-09T10:02:00.000Z` | A / A | `pending` / null | 5 |
| C `33333333-3333-4333-8333-333333333333` | `2026-10-09T10:00:00.000Z` | null / C | `completed` / null | 5 |
| D `44444444-4444-4444-8444-444444444444` | `2026-10-09T10:01:00.000Z` | null / D | `failed` / `unclear_start` | 5 |
| E `55555555-5555-4555-8555-555555555555` | `2026-10-09T10:02:00.000Z` | null / E | `pending` / null | 5 |
| F `66666666-6666-4666-8666-666666666666` | `2026-10-09T10:01:30.000Z` | D / D | `failed` / `low_energy` | 1 |

이 fixture의 기대값은 `counts = { pending: 2, completed: 1, failed: 3, redesigned: 2 }`이고, `histories`의 루트 순서는 `[E, D, C, A]`, 각 `quests`의 ID 순서는 각각 `[E]`, `[D, F]`, `[C]`, `[A, B]`다. 응답에서는 약칭 대신 표의 UUID와 **저장된 전체 quest 객체**를 사용한다. 다음 행동은 B와 E가 모두 `pending`이고 생성 시각도 같으므로 ID가 더 작은 B다: `{ "kind": "resume", "questId": "22222222-2222-4222-8222-222222222222", "rootQuestId": "11111111-1111-4111-8111-111111111111" }`. A·D는 자식이 있으므로 재설계 후보가 아니고, F는 1분이라 재설계 후보가 아니다. B·E를 완료로 바꾼 fixture에서는 F의 `rest_or_create`를 선택한다. D·F가 없는 채 모든 끝 자손을 완료로 바꾸면 `create`를 선택한다. B·E를 완료로 바꾸고 `estimatedMinutes > 1`인 실패 끝 자손을 하나 더 넣으면 그 자손의 `redesign`을 F보다 먼저 선택한다.

### 화면과 실패 표현

시작할 때 저장 파일의 순환·누락 관계가 발견되면 기존 v1 로드 계약처럼 서버 시작을 실패시키고 파일을 자동 보정하지 않는다. 실행 중 확정 스냅샷의 관계나 집계를 완성할 수 없으면 부분 성공 본문 대신 아래의 `500`을 반환한다. 어느 경우에도 조회로 저장 파일을 변경하지 않는다.

저장된 대시보드 응답이 성공적으로 확인되면 상태별 수치 네 개, 루트별 연결 이력, `nextAction`을 함께 갱신한다. `resume`은 선택된 끝 자손의 제목·예상 시간과 기존 완료·실패 기록 조작으로, `redesign`은 해당 실패 이유와 기존 재설계 조작으로 연결한다. `rest_or_create`는 `지금은 1분짜리 행동입니다. 잠시 쉬거나 새 퀘스트를 만들어 보세요.`를 보여 주고 재설계 버튼을 내지 않는다. `create`는 생성 폼으로 연결한다. 루트·부모 관계와 실패 이유는 저장된 객체의 값으로 표시하며 더미 수치나 화면 자체 계산을 성공 결과로 사용하지 않는다.

첫 진입의 생성 폼은 유지하고, 저장 기록이 있으면 다음 행동을 수치보다 먼저 읽을 수 있게 둔다. 수치는 `진행 전`·`완료`·`실패`·`더 작은 행동`의 텍스트 레이블과 숫자를 함께 표시한다. 루트 이력은 루트마다 제목과 순서 있는 단계 목록으로 묶고 현재 끝 자손을 구별하되, 상태를 색만으로 전달하지 않는다. 1280px에서는 읽기 폭을 제한하고 390px에서는 수치·다음 행동·이력을 한 열로 배치해 버튼과 문구가 가려지지 않게 한다. 키보드로 다음 행동, 이력, 오류 재시도에 도달할 수 있어야 한다.

대시보드 최초 로딩, 수동 재조회, 생성·완료·실패·재설계 확정 후 재조회 중에는 새 결과가 확인되기 전까지 이전 수치를 **현재 수치로 표시하지 않는다**. 서버의 조회·집계 실패는 `500 Internal Server Error`와 `{ "error": { "code": "INTERNAL_ERROR", "message": "기록을 불러오지 못했습니다.", "fields": {} } }`를 반환하며, 부분 집계는 성공으로 보내지 않는다. `GET /api/dashboard`의 이 오류, 네트워크 단절, 시간 초과, 형식 오류에서는 집계·이력·다음 행동 영역을 숨기거나 `이전 조회 결과`로 명확히 표시하고 `기록을 불러오지 못했습니다. 다시 시도해 주세요.` 및 `대시보드 다시 불러오기`를 제공한다. 오류를 `0` 또는 `create` 성공처럼 대체하지 않는다. 재시도는 읽기 GET만 반복한다. 잘못된 입력 `400`, 중복·역방향 전이 `409`, 저장 실패 `503`은 기존 구조화된 오류와 저장 불변 계약을 유지한다. POST 응답이 유실되면 기존처럼 목록·이력을 다시 조회해 확정 여부를 확인하고, 확인된 결과만 대시보드에 반영한다.

서버는 빈·복합 fixture에서 집계와 정렬·동률·1분 한계, 요청 전후 스냅샷 동일성, 이전 API 응답과 v1 재시작 호환성을 검증한다. 화면은 성공·빈 상태·읽기 실패·재시도 fixture와 상태 전이 뒤의 새 GET을 검증한다. 같은 통합 head의 QA는 실제 HTTP·브라우저로 생성→완료와 별도 생성→실패 이유→재설계→대시보드, 오류와 저장 불변, 새로고침·재시작, 1280px·390px 조작 및 README 설치·빌드·실행·전체 테스트를 검증한다. fixture 통과만으로 통합 실행을 통과했다고 기록하지 않는다.

## 화면 흐름과 표현

상단에는 목적을 한 문장으로 설명하고 시간 숫자 입력(분), `low`·`medium`·`high` 선택, 생성 버튼을 배치한다. 상태 이름에는 쉬운 한국어 설명을 붙이고 점수·평가처럼 보이게 하지 않는다. 제출 중에는 중복 입력을 막고 진행 상태를 알린다. 성공하면 생성된 행동의 제목, 한 단계 설명, 예상 시간과 저장된 ID에 연결되는 목록 항목을 보여 준다. 목록의 빈 상태에는 다시 입력할 수 있는 안내를 표시한다. 실패하면 폼 근처에 API 메시지를 표시하고 이전 성공 기록을 새 성공처럼 강조하지 않는다.

모바일에서는 입력과 버튼을 한 열로, 데스크톱에서는 읽기 좋은 제한 폭 안에 배치한다. 상태·오류를 색만으로 구분하지 않으며, 키보드로 입력·제출·오류 확인이 가능해야 한다. 2단계에서 `pending` 항목에 완료·실패 행동을 추가하고, 실패 이유 입력과 대안은 원본 옆에서 연결해 보여 준다. 3단계 대시보드 수치와 다음 행동은 저장된 API 결과로 계산하며 하드코딩하지 않는다.

| 2. 기록·재설계 | 완료·실패 전이와 중복 충돌, 실패 이유 저장, 부모·루트 ID 및 축소 불변조건 | 상태·이유·대안 fixture의 문구와 관계 표시 | 실제 HTTP·브라우저로 완료와 실패 각각 수행, 이유별 대안 축소 및 이력 보존 |
| 3. 대시보드·통합 | 저장 데이터 기반 집계와 다음 행동, 전체 오류 회귀 | 빈 상태·복합 이력 fixture의 가독성과 조작 | 같은 통합 커밋에서 전체 흐름·실제 집계·데스크톱/모바일, README 명령의 깨끗한 실행 |

서버와 화면의 fixture 검증은 서로의 미완성 구현을 필요로 하지 않는다. 실제 연결, 브라우저, 서버 재시작 증거는 두 구현을 합친 head의 QA가 남긴다. 2단계 진입에는 1단계의 POST/GET과 저장 불변조건이 수용되어야 하고, 3단계 진입에는 완료·실패·재설계 이력이 실제 저장되어야 한다. 전체 MVP 완료 판단은 각 worker 결과가 아니라 통합 PR의 QA·Reviewer 근거로 한다.
