# Re:Start Quest MVP 구현 계약

## 기준과 결정

이 문서는 `docs/PROJECT_BRIEF.md`의 MVP를 구현할 때 따르는 정본 계약이다. 2026-10-24에 확인한 초기 기준선 `590f15465e9684cbae548268ff6aa7b7ef155dc8`에는 요구사항 문서만 있었으며, 그 SHA에서는 제품 검증이 실행되지 않았다. 아래 내용은 적용할 구현 결정과 수용 기준이지 현재 HEAD의 검증 완료 보고가 아니다.

- **기술:** Node.js 20 이상, 내장 `http`, `fs`, `node:test`와 브라우저의 표준 HTML/CSS/JavaScript를 사용한다. 서버가 정적 화면과 `/api`를 같은 출처에서 제공한다. 필수 런타임 외부 서비스, 유료 AI, 채용 공고 API는 없다. 규칙 기반 생성만 사용한다.
- **저장:** 서버가 JSON 파일 하나를 읽고 쓴다. 로컬 단일 사용자, 단일 서버 프로세스를 MVP의 운영 범위로 둔다. 서버는 기본적으로 `127.0.0.1:3000`에 바인딩하며 `PORT`와 `RESTART_QUEST_DATA_FILE`로 포트와 저장 경로를 바꿀 수 있다. 기본 경로는 작업 디렉터리의 `data/restart-quest.json`이다. 저장소 루트에서 실행할 때 생성되는 `data/` 저장 파일과 같은 디렉터리의 임시 파일은 Git에서 제외한다. 사용자 지정 경로는 이 제외 규칙의 적용 범위를 별도로 확인해야 한다.
- **날짜:** 생성 시각은 UTC ISO 8601 문자열로 저장하고 화면에서는 브라우저의 현지 시각으로 표시한다. “오늘”은 지금 실행할 행동을 뜻하며 일별 생성 횟수를 제한하지 않는다. 대시보드는 날짜와 무관하게 저장된 전 이력을 보여 준다.
- **범위:** 계정, 다중 사용자, 원격 동기화, 외부 배포와 AI 추론은 제외한다. 정신건강 진단이나 개인의 의지 평가는 하지 않는다.

이 선택은 깨끗한 체크아웃에서 별도 서비스 없이 핵심 흐름과 재시작 영속성을 검증하기 위한 것이다. 여러 프로세스가 같은 파일을 쓰는 운영 환경이 필요해지면 저장소를 트랜잭션 DB로 교체해야 한다.

## 데이터와 상태

저장 파일의 최상위 형태는 `{ "schemaVersion": 1, "quests": [...] }`다. 파일이 없을 때만 빈 저장소를 만든다. 형식이 잘못되거나 알 수 없는 `schemaVersion`이면 시작에 실패하고 기존 파일을 덮어쓰지 않는다. API 성공 응답은 해당 변경이 디스크에 기록된 후에만 보낸다. 한 프로세스의 변경 작업은 직렬화하고, 임시 파일을 같은 디렉터리에 쓴 다음 원자적으로 교체해 부분 JSON이 남지 않도록 한다. 저장 실패는 성공으로 위장하지 않는다.

각 퀘스트는 다음 필드를 갖는다. `id`, `rootId`, `parentId`는 UUID 문자열이며, 최초 퀘스트는 `rootId === id`, `parentId === null`이다. 재설계 퀘스트는 직전 퀘스트를 `parentId`로, 최초 퀘스트를 `rootId`로 가리킨다. `createdAt`은 ISO 시각이다. `status`는 `pending | completed | failed`이고, `completedAt`/`failedAt`은 해당 상태에서만 ISO 시각이며 나머지는 `null`이다. `availableMinutes`는 최초 입력값, `currentState`는 생성 시 입력값이며 후손에도 복사한다. `level`은 0~3 정수, `minutes`는 제안한 소요 시간, `title`과 `instruction`은 실행할 행동이다. `failureReason`은 실패 퀘스트에서만 `{ code, note }`이고 다른 상태에서는 `null`이다. 후손의 `redesignReason`은 부모의 실패 이유 코드이고 최초 퀘스트에서는 `null`이다.

`failureReason.code`는 `time | energy | too_hard | unclear | other` 중 하나다. `note`는 선택 항목이며 양끝 공백을 제거한 뒤 Unicode 코드 포인트 기준 0~200자인 문자열이다. 예를 들어 코드 포인트 하나로 된 이모지 200개는 허용하고 201개는 거부한다. 화면과 서버가 같은 기준을 사용하며, 자유 입력은 화면에서 이유 선택을 보조하는 용도로만 저장하고 규칙 판정에는 사용하지 않는다.

상태 전이는 다음과 같다.

| 현재 상태 | 명령 | 결과 |
| --- | --- | --- |
| 없음 | 생성 | 새 `pending` 퀘스트 |
| `pending` | 완료 | 같은 퀘스트가 `completed` |
| `pending` | 실패 이유 기록 | 같은 퀘스트가 `failed`; 재설계 제안 계산 가능 |
| `failed`, 후손 없음, `level > 0` | 재설계 확정 | 더 작은 `pending` 후손 1개 생성; 부모는 `failed` 유지 |

완료/실패의 재호출이나 서로 반대되는 상태 변경은 충돌이다. 부모 한 명당 직접 후손은 최대 한 명이다. 완료한 퀘스트와 아직 실패하지 않은 퀘스트는 재설계할 수 없다. `level === 0`인 실패 퀘스트에는 더 작다고 주장할 수 있는 제안을 만들지 않는다. 이때 화면은 기록을 보존하고 “이미 가장 작은 단계입니다. 새 퀘스트를 만들어 보세요.”라고 안내한다. 실패한 후손도 위 조건을 만족하면 다시 재설계할 수 있다. 종결된 퀘스트의 상태와 실패 이유를 다시 수정하거나 이력을 삭제하지 않는다.

## 규칙 기반 생성과 재설계

생성 입력은 `availableMinutes` 정수 5~120분과 `currentState` 값 `ready | low_energy | overwhelmed`다. 최초 퀘스트의 `level`은 `ready`이고 20분 이상이면 3, `ready` 또는 `low_energy`이고 10분 이상이면 2, 나머지는 1이다. 퀘스트 목록은 실제 채용 공고 없이 사용자의 손으로 할 수 있는 구직 준비 행동이다.

| level | minutes | title | instruction |
| --- | ---: | --- | --- |
| 3 | 20 | 관심 직무 키워드 3개 적기 | 떠오르는 직무 키워드 3개와 그중 하나를 고른 이유 한 줄을 적으세요. |
| 2 | 10 | 관심 직무 키워드 2개와 이유 적기 | 떠오르는 직무 키워드 2개와 그중 하나를 고른 이유 한 줄을 적으세요. |
| 1 | 5 | 관심 직무 키워드 1개와 이유 적기 | 키워드 1개와 관심이 가는 이유 한 줄을 적으세요. |
| 0 | 2 | 관심 직무 키워드 1개 적기 | 지금 떠오르는 키워드 한 단어만 적으세요. |

위 표는 **최초 생성 퀘스트의 행동**이며, 이 계약 이전에 확정된 재설계 후손의 저장 형식이기도 하다. 재설계는 부모의 실패 이유 코드와 `level - 1`로 아래 표의 행동을 결정한다. 모든 이유에서 `3 → 2 → 1 → 0`의 `minutes`는 `20 → 10 → 5 → 2`분으로 줄어든다. `level` 2는 최대 두 후보와 필요한 경우 짧은 이유 한 줄, 1은 후보 하나와 필요한 경우 짧은 이유 한 줄, 0은 한 글자·한 선택·한 단어 중 하나로 과제를 좁힌다. 최초 퀘스트의 `minutes`는 입력 시간 이하이며, 후손은 부모의 `minutes`보다 짧아야 한다. 아래 문구는 실제 실행할 `title`과 `instruction`의 정확한 계약이다. 설명 문구만 이유별로 바꾸고 행동을 동일하게 제안해서는 안 된다.

| 실패 이유 `reasonCode` | 후손 `level` | `minutes` | 제안·후손 `title` | 제안·후손 `instruction` |
| --- | ---: | ---: | --- | --- |
| `time` | 2 | 10 | 직무 키워드 2개만 적기 | 이유를 쓰거나 자료를 찾지 말고, 떠오르는 직무명 두 개만 적으세요. |
| `time` | 1 | 5 | 직무 키워드 1개만 적기 | 자료 조사나 이유 없이 떠오르는 직무명 하나만 적으세요. |
| `time` | 0 | 2 | 직무명 첫 글자 적기 | 떠오르는 직무명의 첫 글자 하나만 적고 멈추세요. |
| `energy` | 2 | 10 | 예시 직무에서 2개 고르기 | 새로 찾지 말고 기획·디자인·개발 중 부담 없는 직무 두 개만 골라 적으세요. |
| `energy` | 1 | 5 | 예시 직무에서 1개 고르기 | 기획·디자인·개발 중 지금 덜 부담스러운 직무 하나만 골라 적으세요. |
| `energy` | 0 | 2 | 예시 직무 하나 표시하기 | 기획·디자인 중 덜 부담스러운 것 하나만 동그라미 치거나 적으세요. |
| `too_hard` | 2 | 10 | 해보고 싶은 업무 동사 2개 적기 | 직무명을 결정하지 말고, 쓰기·만들기·정리하기처럼 해보고 싶은 동작 두 개만 적으세요. |
| `too_hard` | 1 | 5 | 해보고 싶은 업무 동사 1개 적기 | 직무명을 정하지 말고 쓰기·만들기·정리하기 중 해보고 싶은 동작 하나만 적으세요. |
| `too_hard` | 0 | 2 | 업무 동사 첫 글자 적기 | 쓰기·만들기 중 해보고 싶은 동작의 첫 글자 하나만 적으세요. |
| `unclear` | 2 | 10 | 하고 싶은 일 두 칸 채우기 | ‘해보고 싶은 일: ___, ___’의 두 빈칸에 업무 동사 하나씩 넣으세요. |
| `unclear` | 1 | 5 | 하고 싶은 일 한 칸 채우기 | ‘해보고 싶은 일: ___’의 빈칸에 업무 동사 하나만 넣으세요. |
| `unclear` | 0 | 2 | 일의 첫 글자 한 칸 채우기 | ‘해보고 싶은 일: ___’의 빈칸에 떠오르는 업무 동사의 첫 글자 하나만 넣으세요. |
| `other` | 2 | 10 | 관심 직무 키워드 2개와 이유 적기 | 떠오르는 직무 키워드 2개와 그중 하나를 고른 이유 한 줄을 적으세요. |
| `other` | 1 | 5 | 관심 직무 키워드 1개와 이유 적기 | 키워드 1개와 관심이 가는 이유 한 줄을 적으세요. |
| `other` | 0 | 2 | 관심 직무 키워드 1개 적기 | 지금 떠오르는 키워드 한 단어만 적으세요. |

`time`은 조사·이유 쓰기를 덜고, `energy`는 주어진 예시에서 고르게 하며, `too_hard`는 직무 결정 대신 업무 동사로 쪼갠다. `unclear`는 빈칸 형식으로 행동을 구체화하고, `other`는 기존 단계의 일반 행동을 사용한다. `failureReason.note`는 규칙 분기에 사용하지 않는다. 같은 부모 상태와 이유 코드에서는 제안 조회·재조회·확정 시 같은 `level`, `minutes`, `title`, `instruction`을 사용한다. 설명 `rationale`은 기존대로 `time` “필요 시간을 줄였어요”, `energy` “지금 상태에 맞춰 한 단계 줄였어요”, `too_hard` “할 일을 더 작게 나눴어요”, `unclear` “할 일을 구체적인 한 단계로 좁혔어요”, `other` “다시 시작하기 쉽게 한 단계 줄였어요”를 사용한다. 이 행동과 설명은 서버가 생성하며 클라이언트가 임의로 꾸미거나 저장하지 않는다.

저장 파일의 `schemaVersion`은 1로 유지하고 퀘스트 필드를 추가하지 않는다. 이미 저장된 최초 퀘스트는 위 첫 표의 행동을 그대로 유지한다. 이미 저장된 후손도 기존 고정 단계 표의 `title`·`instruction`·`minutes`를 사용했다면 부모의 `failureReason.code`에 관계없이 유효한 이력으로 읽는다. 새 후손은 이유별 표의 정확한 문구로 저장한다. 저장 검증은 후손의 `title`·`instruction`이 **부모의 이유에 맞는 새 행동 한 쌍** 또는 **기존 고정 단계의 행동 한 쌍**과 일치하는지 확인하고, 기존 ID·상태·시각·부모 관계·`redesignReason`·단계·시간 검증은 유지한다. 읽기나 상태 변경 중 기존 후손의 저장 문구를 새 문구로 바꾸지 않는다. 기존 후손이 나중에 실패하면 그 후손의 새 제안은 그때 기록한 실패 이유와 현재 이유별 규칙으로 계산한다.

## HTTP API

API 성공·오류 응답과 본문이 있는 변경 요청은 UTF-8 JSON이다. 모든 변경 `POST`는 빈 본문을 허용하는 완료·재설계 요청까지 `Content-Type: application/json`을 요구한다. `charset` 매개변수가 있으면 UTF-8만 허용하며, 헤더가 없거나 다른 미디어 타입·문자 인코딩이면 본문을 해석하거나 저장하기 전에 `415 UNSUPPORTED_MEDIA_TYPE`으로 거부한다. `Origin` 헤더가 있으면 서버가 실제로 요청을 받은 로컬 주소와 포트의 `http` 출처와 일치해야 한다. `Origin: null`, 다른 주소·포트·스킴은 본문을 해석하거나 저장하기 전에 `403 FORBIDDEN_ORIGIN`으로 거부한다. 비교 기준은 요청의 `Host` 헤더가 아니라 수신 소켓의 주소와 포트다. 브라우저 밖 클라이언트의 `Origin` 없는 JSON 요청은 허용한다. 거부된 요청은 저장 이력을 바꾸지 않는다.

성공 시각과 ID는 서버가 만든다. 알 수 없는 필드, 잘못된 타입/범위, 잘못된 JSON, 과도한 본문은 거부한다. 본문 크기 상한은 1 MiB다. 입력 오류는 `400 VALIDATION_ERROR`(상한 초과는 `413 PAYLOAD_TOO_LARGE`), 없는 ID는 `404 NOT_FOUND`, 잘못된 상태는 `409 INVALID_STATE`, 이미 후손이 있으면 `409 ALREADY_REDESIGNED`, 최소 단계 재설계는 `409 MINIMUM_STEP`, 저장 실패는 `500 STORAGE_ERROR`다. 오류 형식은 `{ "error": { "code": "...", "message": "..." } }`이고 사용자에게 보여 줄 수 있는 한국어 `message`를 반환한다. 내부 파일 경로나 스택은 노출하지 않는다. 메서드가 틀리면 `405 METHOD_NOT_ALLOWED`다.

| 요청 | 본문 | 성공 응답 |
| --- | --- | --- |
| `POST /api/quests` | `{ "availableMinutes": 20, "currentState": "ready" }` | `201 { "quest": Quest }` |
| `POST /api/quests/:id/complete` | 빈 본문 또는 `{}` | `200 { "quest": Quest }` |
| `POST /api/quests/:id/fail` | `{ "reasonCode": "time", "reasonNote": "회의가 길어짐" }`; `reasonNote` 선택 | `200 { "quest": Quest, "suggestion": Suggestion }` |
| `POST /api/quests/:id/redesign` | 빈 본문 또는 `{}` | `201 { "quest": Quest, "parentQuest": Quest }` |
| `GET /api/dashboard` | 없음 | `200 { "summary": Summary, "quests": Quest[], "nextActions": Quest[], "suggestions": Suggestion[] }` |
| `GET /api/health` | 없음 | `200 { "status": "ok" }` |

`Suggestion`은 `{ "parentId", "level", "minutes", "title", "instruction", "reasonCode", "rationale" }`이고 아직 저장된 퀘스트가 아니다. `POST .../fail` 성공 후 즉시 계산되어 반환되며, 새로고침 후에도 대시보드의 `suggestions`에서 같은 실패 기록에 대해 다시 계산된다. `level === 0`이면 실패 응답의 `suggestion`은 `null`이다. 확정 요청만 실제 후손을 저장하며, 이미 후손이 있는 부모는 제안 목록에서 빠진다.

새 제안의 `title`·`instruction`은 위 이유·단계 표에서 선택하며, `POST .../redesign`으로 저장한 후손의 네 필드 `level`·`minutes`·`title`·`instruction`은 직전 `Suggestion`과 같아야 한다. 제안의 `reasonCode`와 후손의 `redesignReason`은 부모의 `failureReason.code`와 같다. 이미 저장된 후손의 행동 문구는 대시보드에 저장된 그대로 반환한다.

`Summary`는 `{ "total", "pending", "completed", "failed", "redesigned" }`이다. 앞의 네 숫자는 저장된 퀘스트를 상태별로 센 값이고 `redesigned`는 `parentId !== null`인 퀘스트 수다. `quests`는 `createdAt` 내림차순(동시각이면 `id` 순) 전체 이력이다. `nextActions`는 저장된 `pending` 퀘스트만 같은 정렬로 담는다. 대시보드의 숫자와 목록은 매 요청마다 저장 파일에서 읽은 결과로 만들며 예시 데이터나 클라이언트 캐시를 섞지 않는다.

## 화면과 오류 처리

단일 페이지 `/`에 생성 입력, 다음 행동, 이력과 요약을 둔다. 첫 화면에서 시간을 숫자로 입력하고 상태를 선택해 생성한다. 생성 성공 시 서버 응답으로 대시보드를 다시 조회하고 새 `pending` 퀘스트의 행동·예상 시간을 보여 준다. 완료 버튼은 성공 후 완료 시각과 요약을 반영한다. 실패 버튼은 이유 선택과 선택적 메모 입력을 연다. 실패 저장 후 서버의 `suggestion`을 원래 퀘스트 아래에 보여 주고 “더 쉬운 퀘스트 만들기”로 확정한다. 후손 카드에는 “원래 퀘스트 → 새 행동” 관계와 실패 이유를 보이며 후손도 완료/실패할 수 있다. 새로고침 뒤에도 같은 기록과 다음 행동이 나타난다.

데스크톱에서는 입력과 요약을 상단에, 다음 행동과 이력을 읽기 쉬운 영역에 놓는다. 모바일 375px 폭에서는 세로 한 열로 쌓고 가로 스크롤 없이 모든 입력·버튼·제안을 사용할 수 있게 한다. 폼에는 연결된 라벨을, 처리 중에는 중복 제출 방지를, 오류에는 `role="alert"`를 제공한다. 실패 메모는 양끝 공백을 제거한 뒤 Unicode 코드 포인트 200개를 초과하면 화면에서 오류를 표시하고 전송하지 않는다. 브라우저의 UTF-16 코드 단위 `maxLength`로 입력을 제한하지 않는다. API 실패 시 저장되지 않은 성공 상태를 화면에 미리 표시하지 않고 오류 메시지와 재시도 경로를 보여 준다. 새로고침은 항상 `GET /api/dashboard`로 시작한다.

## 구현 순서와 실행 계약

1. 저장소/규칙/API를 구현하고 순수 규칙 테스트와 실제 HTTP·재시작 테스트를 만든다. 저장 실패, 잘못된 입력과 충돌 응답까지 확인한다.
2. 같은 출처의 화면을 API에 연결한다. 프론트는 위 요청/응답 형식을 사용하고 저장된 대시보드에서만 확정 상태를 렌더링한다.
3. `scripts/verify.mjs`를 검증 진입점으로 만들고 API/영속성 및 실제 데스크톱·모바일 브라우저 흐름을 통합 검증한다. `README.md`와 비밀값 없는 설정 예제를 실제 명령에 맞게 작성한다.

저장소의 실행 계약은 `npm ci`로 의존성을 준비하고 `npm start`로 로컬 서버를 시작하며 `npm test`로 단위·API 회귀 테스트를 실행하는 것이다. `package.json`과 잠금 파일을 함께 둔다. 설정 예제에는 `PORT`와 `RESTART_QUEST_DATA_FILE`만 넣는다. 기본 저장 경로는 개발 중에도 유효해야 하며, 저장소 루트의 `data/`와 그 안의 원자적 저장 임시 파일은 `.gitignore`로 제외한다. 테스트는 임시 저장 경로를 사용해 사용자 데이터를 건드리지 않는다. 실제 구현에서 명령이 달라지면 코드와 README를 함께 맞추고 이 계약도 갱신한다.

## MVP 수용 기준과 검증 증거

`node scripts/verify.mjs --playwright-module=<Playwright 모듈 절대 경로> --artifacts-directory=<체크아웃 밖 경로>`가 프로젝트 소유 검증 진입점이다. 제공된 모듈을 실제로 import해 브라우저를 시작한다. 의존성 준비와 서버 시작/종료를 스크립트 안에서 처리한다. 브라우저 실행이 불가능하거나 필수 흐름이 건너뛰어지면 실패 코드로 종료한다. 스크립트는 각 실행에 별도 임시 데이터 파일을 사용하고 성공·실패 모두에서 자식 서버를 중지한다. 스크린샷과 검증 결과는 지정된 체크아웃 밖 아티팩트 경로에 남긴다. 호스트가 이 명령을 깨끗한 분리 체크아웃에서 실행하며, 로컬 실행 주장과 호스트의 수용 증거를 구분한다.

검증은 같은 통합 커밋에서 다음을 실제로 단언해야 한다.

- 실제 HTTP로 생성 입력 범위/타입 오류, 실패 이유 오류, 없는 ID, 중복 완료·실패, 완료 후 실패, 실패 후 완료, 재설계 중복과 최소 단계 오류의 상태 코드·오류 본문을 확인한다.
- 모든 변경 `POST`에서 JSON `Content-Type`을 확인한다. 빈 본문을 허용하는 완료·재설계도 같은 헤더를 요구하고, `text/plain` JSON 및 헤더 없는 요청을 거부하는지 검사한다. 실제 수신 주소·포트와 같은 `Origin` 및 `Origin` 없는 JSON 요청은 허용하고, 다른 출처·`null` 출처는 거부하는지 상태 코드·오류 본문과 저장 이력 불변성으로 확인한다.
- 기본 `data/` 저장 파일과 같은 디렉터리의 임시 파일이 Git에서 제외되는지 확인한다. API와 실제 브라우저에서 양끝 공백 제거 후 Unicode 코드 포인트 기준 이모지 메모 200개는 저장되고 201개는 오류가 표시되며 저장되지 않는지 확인한다.
- 생성 → 완료와 별도의 생성 → 이유를 기록한 실패 → 제안 조회 → 재설계 확정 → 새 행동 완료를 수행한다. 부모·후손의 ID 관계, 더 낮은 `level`, 짧은 `minutes`, 요약과 다음 행동 목록을 HTTP 응답 및 저장된 결과와 대조한다.
- 같은 부모 `level`에서 `time`, `energy`, `too_hard`, `unclear`, `other`를 각각 기록하면 다섯 제안의 `title`과 `instruction`이 이유별 표에 맞게 달라지는지 확인한다. 부모 `level` 3·2·1을 모두 확인하고, `rationale` 차이만으로 통과시키지 않는다. HTTP의 실패 응답·대시보드 제안·확정된 후손·새로고침·서버 재시작 뒤 저장 이력에서 행동 문구와 낮아진 `level`·`minutes`가 일치해야 한다.
- 이전 고정 단계 행동으로 저장된 후손이 있는 `schemaVersion: 1` 파일을 다시 열어 기존 `title`·`instruction`을 보존하는지 확인한다. 그 후손의 실패 이유 기록과 새 이유별 재설계를 해도 기존 이력과 부모·후손 관계가 유지되어야 한다.
- 성공 직후 페이지 새로고침과 서버 프로세스 재시작 후 대시보드를 다시 읽어 완료·실패·재설계 이력과 다음 행동이 유지됨을 확인한다. 성공 응답 후 파일 저장이 안 된 경우는 실패로 처리한다.
- 실제 데스크톱 및 모바일 브라우저에서 입력, 생성, 완료, 실패 이유, 제안 확정, 새 행동 수행, 대시보드 반영을 DOM 상호작용으로 확인하고 각 화면의 스크린샷을 남긴다. 모바일은 가로 넘침과 핵심 조작 가능 여부를 확인한다. API 오류를 유도해 사용자에게 오류가 보이고 허위 성공 상태가 나타나지 않는지도 확인한다.
- 데스크톱과 375px 모바일의 실제 브라우저 흐름에서도 같은 부모 단계에서 서로 다른 실패 이유를 선택해 제안의 실행 행동이 다름을 확인한다. 제안 확정 뒤 카드와 새로고침 뒤 이력에 해당 이유의 `title`·`instruction`이 그대로 남아야 한다.
- 실행 결과에는 검증 대상 SHA, 명령, 통과/실패, 아티팩트 위치를 기록한다. QA와 리뷰어는 통합 HEAD와 실제 실행 결과를 별도로 확인한다. 이 문서 자체의 커밋이 그 커밋을 검증했다고 주장하지 않는다.

초기 기준선 `590f15465e9684cbae548268ff6aa7b7ef155dc8`에서는 위 검증이 **미실행**이었다. 이후 검증 이력은 실제로 관측한 SHA와 시점에 연결해 보고하며, 과거 SHA의 결과를 이 변경이 통합된 현재 HEAD의 통과 증거로 사용하지 않는다.
