# 프로젝트 브리프

## 목적

AgentFlow가 실제 팀처럼 제품을 조사하고, 설계하고, 병렬 구현하고, 검증하고, 릴리스 후보까지 완주할 수 있는지 확인한다. 결과물은 취업용 포트폴리오로 설명할 수 있을 만큼 문제 정의와 기술적 깊이가 분명해야 한다.

## TASK-002 제품 선정 결과

TASK-002의 명시적 요청에 따라 첫 구현 제품은 **Re:Start Quest**로 확정한다. 새 제품 후보를 다시 고르는 대신, 아래에 보존된 문제 인식을 익명 사용자가 한 번의 방문에서 검증할 수 있는 작은 재진입 루프로 구현한다.

- 대상 사용자: 취업 준비가 중단되었고, 무엇부터 다시 해야 할지 몰라 시작을 미루는 사람
- 핵심 문제: 큰 계획과 죄책감이 실제 행동 재개를 방해한다.
- 차별적 상호작용: 실행하지 못한 이유를 기록하면 같은 목표를 더 작은 다음 행동으로 즉시 바꾼다.
- 첫 릴리스 성공 기준: 신규 사용자가 가입 없이 상태를 입력하고, 행동을 완료하거나 더 쉬운 행동으로 바꾼 뒤, 새로고침 후에도 기록과 다음 행동을 확인한다.
- 정본 설계: [MVP 설계](MVP_DESIGN.md)

경쟁 서비스의 기능 수를 따라가는 것은 이번 선택의 근거가 아니다. AI 이력서 작성, 채용 공고 수집, 커뮤니티 대신 상태 전이와 실패 복구 루프를 구현해 도메인 깊이를 보여준다.

## 보존할 문제 인식

초기 아이디어인 Re:Start Quest는 취업 공백자가 실패 후에도 더 작은 행동으로 다시 시작하도록 돕는 구직 행동 재진입 엔진이었다. 단순 취업 정보 모음이나 이력서 생성기가 아니라 다음 흐름을 핵심으로 삼았다.

```text
현재 상태 파악
-> 오늘 실행할 작은 행동 제안
-> 실패 이유 기록
-> 더 쉬운 행동으로 재설계
-> 실행 기록과 다음 행동 연결
```

이 문제 인식은 TASK-002에서 제품 주제로 확정되었다. 상세 범위와 구현 계약은 정본 MVP 설계를 따른다.

## 새 제품 선정 기준

- 실제 사용자가 겪는 구체적인 반복 문제를 해결하는가
- 기존 서비스와 다른 핵심 상호작용을 한 문장으로 설명할 수 있는가
- 단순 LLM 포장이나 기능 모음이 아닌 도메인 모델과 상태 변화가 있는가
- 프론트엔드, 백엔드, 데이터, AI, 테스트 역량을 자연스럽게 보여주는가
- 개인 프로젝트 범위에서 완성하고 배포하고 시연할 수 있는가
- 사용자가 결과를 직접 확인할 수 있는 명확한 핵심 시나리오가 있는가

## 첫 회의의 산출물

1. 후보 문제 3개와 대상 사용자
2. 경쟁 서비스와 대체 행동 조사
3. 후보별 차별점, 구현 난이도, 포트폴리오 설명력 비교
4. 선택한 문제의 핵심 사용자 여정
5. MVP 범위와 명시적인 제외 범위
6. 자동 검증 가능한 완료 조건

TASK-002의 원문 요청에 따라 위 제품 선정 결과와 MVP 설계를 첫 회의 결론으로 기록한다. 이후 구현은 정본 설계의 패키지 경계와 통합 완료 조건을 따라야 한다.
